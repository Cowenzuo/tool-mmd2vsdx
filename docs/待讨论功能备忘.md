## P-6 接入形态收敛为本地 HTTP 服务（部分落地）

> 定案 2026-09-23。结论是**服务化**：一个本机常驻进程，原生字节进出，
> 不落盘、不吃路径参数。契约写在 `docs/接口协议.md`，本节只记为什么这么定，
> 以及被否掉的方案。

### 背景

调用方是文档编辑器一类的工程，使用场景在本机：它要的是"给我 mermaid 原文，
还我 `.vsdx` 字节"，然后自己决定落盘、命名与嵌入。原先考虑过让编辑器自行拉起
我们的进程、传 mmd 文件路径与输出目录；讨论中发现这条路会引入控制端问题：
多个对等调用方共用常驻进程时，谁拉起、谁关、版本谁说了算，都没有自然答案。

### 决策依据（2026-09-23 实测）

| 场景 | 耗时 |
| --- | --- |
| 命令行单张图，每次独立进程 | 1.23 到 1.27 秒；首次 7.5 秒属冷盘一次性开销 |
| 同进程批量 9 张，一次调用 | 1.57 到 1.60 秒 |

也就是说，冷启动固定开销约 1.2 秒，稳态边际成本约 40 毫秒每张。每张图起一次进程
在"一篇文档多张图"下不可接受；常驻之后每张只花几十毫秒，服务化因此成立。

### 结论

- 对外唯一入口是本机 HTTP 服务：`POST /convert` 送原文，响应体是 `.vsdx` 字节；
- **不落盘、不接受路径参数**：没有输出目录、没有覆盖开关、没有临时文件；
- 固定端口 `12138`，常驻不退，空闲只回收 Chromium，进程留着；
- 安全只做回环监听、`Host` 校验、不发 CORS 头，不需要 token。这套结论的前提是
  不落盘，属于红线：一旦加回路径能力，安全结论立即作废；
- 命令行与库入口移除，不再作为对外承诺。

### 被否方案

| 方案 | 否决理由 |
| --- | --- |
| 每张图调一次命令行 | 每张 1.2 秒固定开销，文档里十几张图就十几秒 |
| 命令行一次转整篇 | 只解决多图；调用方仍要管进程与临时文件，拿到字节还要多一次落盘 |
| 库引入（同进程调用） | 调用方必须是 Node 且与我们同进程，浏览器生命周期压在宿主上 |
| 编辑器拉起加路径模式 | 引入越权读写面，要授权白名单与 token；而调用方本来要的是字节 |
| 固定端口加多调用方共享加租约生命周期 | 控制端问题：多个对等调用方之间，拉起、关闭与版本没有自然归属 |
| 产物句柄与下载端点 | 本机内存足够，句柄表是共享部署才需要的复杂度 |
| 上传走 multipart 或 base64 包体 | 本机回环下多一层编解码，不如原文进、字节出直接 |

### 下一步

契约已在 `docs/接口协议.md`。剩余收尾是测试与结构文档同步，
远程形态与鉴权见 P-5。

## P-1 自产物预览渲染器（记录归档）

> 场景：另一工程用 OpenXML 构造 docx，嵌入本工程转出的 vsdx 时，嵌入处需要一张预览图。
> **结论：不自产。** 缺预览不影响 vsdx 打开，也不影响 Word 里的显示；复刻 Visio 观感
> 属装饰性投入，不做。原先的自研光栅化方案随之作废。

### 决策依据（2026-09 实测）

- **Word 嵌入处那张图与 vsdx 包内缩略图无关**：它是插入时由 OLE 服务器（注册表实测
  `.vsdx → Visio.Drawing.15`）现场渲染、并存进 **docx 自己的包**（`word/media/image1.emf`）；
  我们那份 vsdx **没有 thumbnail 部件**，Word 照样出了正确的图；
- **资源管理器图标会自愈**：Visio 首次"改动并保存"时自动补封面。实测三种情形——
  缺则补（14432 B）、有且只打开不改则原样保留、有且改动则重画（15404 B）；
- **自产等于复刻渲染引擎**：与 Visio 的剩余差距在布局层（菱形出入点、节点尺寸、
  整体宽高比约 10%），不是调主题参数能消掉的；自研光栅化是另一个量级的工作量。

### 留档事实（将来若要重启）

| 项 | 结论 |
| --- | --- |
| Word 嵌入结构 | `word/embeddings/<名>.vsdx`（裸 zip，非 CFB）加 `word/media/image1.emf`，再由 `<w:object>` 与两条关系串起；docx 可自造 |
| 嵌入会重写文件 | 源 10357 B → 文档内 17703 B，`visio/document.xml` 5029→21730，母版被换成 Visio 的 |
| 自产 EMF | .NET 8 加 Svg.NET 可跑通（SVG→EMF，450 条矢量记录）；PowerShell 5.1 加三个 DLL 遇 `<text>` 抛 GDI+ 参数错误，不可用 |
| mermaid 出预览 | 线宽取 Visio 实测 0.75pt（折合 1px）；直角折线用 `curve: stepAfter`；`step` 与 `stepBefore` 末段零长度，会让箭头朝向失效 |

### 消费方如确需预览

自行渲染或留空。本工程不产出预览图，也不写 `docProps/thumbnail.emf`——该部件在 OPC 中
可选，写法见 `docs/VSDX解压结构研究/通用visio结构分析.md` 4.4。

## P-5 MCP 远程接入（待施工）

> 本条是 alpha3 期间的调研与设计结论：**代码实现已回退**，只留方案与缺口清单，
> 等有真实调用方时再开工。alpha3 交付的是本机 HTTP 服务，契约见
> `docs/接口协议.md`；P-6 定案后 MCP 只剩协议壳与远程所需的鉴权。

### 背景

目标：让外部 agent（DSH 会话、Claude Code、Cursor 等）直接调用本工程的转换能力，
不必让模型现场写 Node 脚本。

alpha3 一度按 MCP 做完了两条传输（stdio 与流式 HTTP）并在真实客户端验通，
但要达到"能对外开"的程度，还要补鉴权、产物句柄、容器化与多副本语义，周期不可控，
于是回退成待办。

### 已定的设计（可直接复用）

- 传输：Streamable HTTP（远程；无状态单端点 `/mcp`，每个请求独立建 server 与
  transport），请求体直接带 mermaid 原文，响应体直接带产物字节，本机形态下不需要
  产物句柄。原先还设计了 stdio 传输，P-6 定案后不再有子进程形态，那条随之作废；
- 工具四个：`mmd2vsdx_convert`、`mmd2vsdx_validate`、`mmd2vsdx_convert_batch`、
  `mmd2vsdx_inspect`。P-6 之后本地只保留转换与健康检查两个入口，工具面要按新契约
  重新收一遍；
- 资源三个：`mmd2vsdx://capabilities`、`mmd2vsdx://samples`、`mmd2vsdx://samples/{name}`；
- 依赖官方 `@modelcontextprotocol/sdk`，协议版本随 SDK 走；
- 生命周期：Chromium 惰性启动、渲染串行队列、空闲回收、退出清理。

### 上云前必须补的缺口

| # | 缺口 | 说明 |
| --- | --- | --- |
| 1 | 鉴权 | 现在没有任何校验；至少要静态 Bearer token，规范方向是 OAuth 2.1 与 OIDC 发现 |
| 2 | 产物句柄 | 只有远程上传下载的形态才需要；本机形态响应体直接带字节，不用句柄 |
| 3 | 多副本 | 本机不涉及；对外开之后仍要决定按 id 粘住还是共享存储 |
| 4 | 容器与 Chromium | 镜像要带 Playwright 系统依赖；容器内以 root 跑必须显式关 Chromium 沙箱 |
| 5 | 并发与配额 | 本机已落地：队列上限 32、单请求超时 15 秒、超限回 429；对外开之后要按调用方配额 |
| 6 | 监听与 TLS | 默认只监听回环，对外要显式指定并放在反向代理后面 |
| 7 | 协议版本 | SDK 1.30.0 仍是 2025-11-25；2026-07-28 的无状态核心（每请求 `_meta`、`server/discover`）等稳定版 |

### 客户端接法（已查证）

- DSH：在 profile 的 `cordis.patch.yml` 加一条 `@deepseek-ai/dsh-mcp-client`，
  `transport: streamable-http`，配 `url` 与 `headers`，headers 正好放静态 token。
  模型看到的工具名是 `mcp__<serverName>__<原名>`；子进程环境会清洗掉含
  KEY/PASSWORD/SECRET/TOKEN 的变量与 `DSH_*`，要传的配置写进 `config.env`。
  stdio 那条配置随 P-6 作废；
- 注意 DSH 目前**只桥接 Tools，不桥接 Resources 与 Prompts**，所以能力清单不能只放资源，
  最好同时提供一个 `mmd2vsdx_capabilities` 工具；
- 其它宿主：Claude Code、Claude Desktop、Cursor 用 `mcpServers` 配置，走 streamable-http。

### 下一步

按缺口顺序推进：先做 token 鉴权与对外监听的 TLS 终结，再补容器化，
最后按真实调用方的形态决定"单副本按 id 粘住"还是"共享存储"。
本机的并发上限、单请求超时与空闲回收已经在 P-6 落地，不用重做。

## P-4 画布贴合（部分落地）

### 背景

早期只有 sequence 分支写 `DrawingResizeType=2`，class 与 er 还是 `1`，而且内容盒
取自 mmd 的 SVG viewBox（固定 800×600），与内容无关。后果是 Visio 打开时按打印纸
倍数放大页面并整体平移图形：ER 写入 15.34×10.27IN 被打开成 16.04×11.69IN，
sequence-3 写入 11.96×8.01IN 被打开成 23.80×11.69IN 且形状整体右移 7.77IN。

### 结论

页面尺寸等于内容外包围框加两倍半线宽，`kCanvasMargin = 0.0053IN`；全图型
`DrawingResizeType=2`；内容盒按图型精确计算，不再用 viewBox。落地口径见
`docs/开发过程/02-数据流与画布.md` 第三节，现象与机制见
`docs/VSDX处理经验/02-坑位与解法.md` 7.11。

### 下一步

1. 审计器把成员行宽度公式 `LISTSHEETREF()!Controls.ROW_1` 映射为容器宽：
   class 与 er 现在被误报越界（class 左侧 0.22IN、er 右侧 0.24IN）；
2. 审计器补 `Sheet.5!Height−Height` 这类公式求值：sequence 片段参数带（MS7）
   现在被母版默认 PinY 误定位；另外底部固定多出 0.005IN（端点半线宽）；
3. 把"页面等于内容盒加减容差"的审计断言并入 `tests/spec.test.ts`，
   现在只有 sequence 断言了 `DrawingResizeType=2`。

### 关联

- 审计脚本 `docs/VSDX处理经验/scripts/canvas-audit.mjs`：母版继承解析、旋转、
  迷你公式求值、NoShow 跳过；
- 选项位置 `source/diag/common.ts` 的 `RenderOptions.drawingResizeType/pageMargin`，
  包内私有，随各 render 函数的入参传递；
- 当年的探针脚本随 `temp/` 清理，需要时按
  `docs/VSDX处理经验/03-工具与脚本手册.md` 重建。

## P-3 docProps 字段差异（记录归档）

| 文件 | Visio 保存的 | 本工具生成 |
| --- | --- | --- |
| core.xml | 作者为系统账户、完整时间戳、语言等全字段 | 仅 title 与 creator 为 mmd2vsdx |
| app.xml | Application 为 Microsoft Visio、HeadingPairs/TitlesOfParts 统计、AppVersion 16.0000 | Application 为 mmd2vsdx、AppVersion 2.0 |
| custom.xml | BuildNumberCreated/Edited、IsMetric、TimeEdited | 同结构，加 `RecalcDocument=true` |
| thumbnail.emf | 有，首页矢量封面，保存时生成 | 无 |

字段全集与结构一致，本工具按最小必要填写；解析器按元素名读取，缺省字段按空处理，
不影响打开。需要时（对接方或文档库要求作者、统计、封面预览）再按上表补齐；
thumbnail 一项见 P-1（已决定不自产）。
