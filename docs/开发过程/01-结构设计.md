# 01 结构设计（目标结构）

> 本文是重做时定下的目标结构：分层、两个契约、每层的职责与边界。
> 实现已按此落地，所以本文只写**机制与约定**；文件清单、函数签名这类
> 会随代码变化的细节以 `source/` 为准，本文不再维护。

## 一、分层与依赖

| 层 | 目录 | 说明 |
| --- | --- | --- |
| L0 契约层 | `source/contracts/` | 契约 A（图型 json）、契约 B（部件清单），纯类型加校验，零依赖 |
| L1 底层 | `source/common/xml/`、`source/opc/` | XML 树与序列化、OPC/ZIP 容器，不含业务语义 |
| L2 公用库 | `source/common/` | 几何、单元格、公式、文本、样式、母版、端口 |
| L3 解析层 | `source/parser/` | Chromium 加 mermaid 出快照，再归一化成契约 A |
| L4 转义层 | `source/diag/` | 四个平级图型包，契约 A 变成页面部件 |
| L5 打包层 | `source/xml-parts/`、`source/squeeze/` | 部件组装校验，再压成 OPC/ZIP 字节 |
| L6 编排层 | `source/convert.ts` | 按 `kind` 分派，管线内的顶层 |
| L7 适配层 | `source/service/` | 转换、校验、检视、批量四个能力，库 API 与命令行共用 |
| L8 接入层 | `source/cli/` | 四个子命令与退出码，只依赖适配层 |

依赖只允许自上而下，跨组白名单是：`convert` 到其余全部；`parser` 到
`contracts`、`common`；`diag` 到 `contracts`、`common`；`xml-parts` 到
`contracts`、`common`、`opc`；`squeeze` 到 `contracts`、`opc`；`opc` 到
`common`；`common` 到 `contracts`；`service` 到 `contracts`、`common`、`parser`、
`xml-parts`、`squeeze`、`convert`；`cli` 到 `service`。实测文件数与边数见
[02-数据流与画布.md](02-数据流与画布.md)，落地约定与守门口径见
`docs/AI开发约定/项目特定规范.md`。

## 二、契约 A：图型 json

契约 A 是 parser 的唯一输出、图型包的唯一输入，一份"画了什么"的中间态。
它解决三件事：parser 与图型包解耦；图型包之间互不 import，判断只认 `kind`；
各图型有独立字段块，class 的成员、ER 的主键不挤在通用字段里。

```
ContractA {
  kind: DiagramKind;              // flowchart | block | class | er | sequence
  meta: Meta;                     // 标题、方向、像素边界、原始文本
  shapes: GenericShape[];         // 通用骨架（扁平图类）
  edges: GenericEdge[];           // 通用边（含 waypoints 与箭头）
  clusters: Cluster[];            // 子图簇
  classModel?: ClassModel;        // class 专用
  erModel?: ErModel;              // ER 专用
  sequence?: SequenceModel;       // sequence 专用
}
```

通用骨架：

| 类型 | 字段要点 | 说明 |
| --- | --- | --- |
| GenericShape | id、label、shapeKind（rect、roundRect、diamond、circle、ellipse）、x、y、width、height、fill、styleClass、parentId、lifelineKind、dividers | 几何像素值直接来自快照 |
| GenericEdge | from、to、label、style（normal、dotted、thick）、arrowHead、arrowTail、waypoints、fromMultiplicity、toMultiplicity | 多重性只有 ER 关系在用 |
| Cluster | id、label、x、y、width、height | 子图簇 |

图型扩展块：

| 类型 | 关键字段 | 说明 |
| --- | --- | --- |
| ClassModel | classes[]（name、stereotypes、attributes[]、operations[]）、relations[]（from、to、kind）、layout | 类三栏盒与关系语义 |
| ErModel | entities[]（name、attributes[]：name、type、primaryKey、foreignKey、required）、relations[]（from、to、label、两端多重性、identifying） | 主键与外键语义 |
| SequenceModel | actors[]（id、label、kind 为 object 或 actor）、messages[]（from、to、label、kind）、activations[]、fragments[] | 消息语义与激活区间 |

约定与边界：

- 契约 A 只存语义与像素几何，不含任何 Visio 字段：没有 cell、没有样式 ID、
  没有母版名；
- 像素坐标统一按"SVG 向下为正"，换英寸在公用库几何组做；
- 新增图型走独立包，不改本契约骨架；不支持的图型在解析层直接抛错，
  不做骨架兜底，避免被静默降级成流程图；
- 类型与默认工厂在 `contracts/a.ts`，运行时校验与兜底在 `contracts/a-guards.ts`。

## 三、契约 B：部件清单

契约 B 是图型包的唯一输出、压缩库的唯一输入，一份"完整的 vsdx 内容"。
它让画图与打包彻底分开：图型包产出部件数据，不碰 zip；压缩库只认数组，
不认 Visio 语义。

```
XmlPart {
  uri: string;           // 规范部件 URI，如 /visio/pages/page1.xml
  contentType: string;   // 部件媒体类型
  xml: string;           // 部件 XML 文本，含声明行
}

ContractB {
  parts: XmlPart[];      // 全部部件：页面、母版、文档、属性、登记表
}
```

约定与边界：

- `parts` 顺序即打包顺序，先登记表后内容，压缩库不重排；
- uri 必须唯一，部件之间靠 uri 相对关系互相引用；
- 图型包只产出页面、母版、文档基座三类部件；docProps、`[Content_Types].xml`、
  `_rels/.rels` 由 xml 部件栈补齐；
- 图型包产出前必须过 xml 部件栈的校验，保证每份 xml 完整可解析。

## 四、解析层 parser

parser 是管线第一段：mermaid 文本变成契约 A。它负责把图翻译成结构，
不懂任何 Visio。渲染在进程内 Chromium 完成，注入 mermaid 与提取脚本，
提取结果回到 Node 侧归一化。

```
source/parser/
├── index.ts              门面 Parser：串行队列与 convertText
├── renderer.ts           Chromium 生命周期：启动、复用、失败重建
├── ext/                  浏览器端提取脚本
│   ├── bridge.mjs        页面桥：取 mermaid 真实图型名，分派提取器
│   ├── generic.mjs       通用 SVG 提取（flowchart、block）
│   └── class.mjs  er.mjs  sequence.mjs
└── normalize/
    └── generic.ts        快照归一到契约 A，含 kind 判定
```

机制要点：

- 支持判定靠 mermaid 的真实图型名。`getDiagramFromText` 拿到的类型名进快照，
  归一化层对照 `kImplementedKinds`，不在清单里就抛错，绝不落到通用分支；
- 专用提取器只读 mermaid 的图结构与渲染出的 DOM，不做布局计算，
  布局像素直接用 mermaid 的结果；
- 归一化是零浏览器依赖的纯函数，可以单测。

边界与注意：

- parser 不产出任何 `.xml` 字符串；失败抛 `[parse]` 前缀的错误；
- 新增图型要写一个提取器加一个归一化分支，注册到分派表，不动其它图型；
- 契约 A 的校验与兜底在契约层，不在本包。

## 五、公用库 common

公用库是各图型包共享的零件箱，把 Visio 语义层的通用能力收拢，不含任何
图型判断。

```
source/common/
├── index.ts              门面 CommonKit（服务容器）
├── intents.ts            意图类型：形状、边、端口
├── units.ts              单位与比例常量
├── geometry/             box.ts 矩形/圆角/椭圆/菱形几何行；transform.ts 像素换英寸与 y 翻转
├── cells/                writer.ts 单元格写手：V/U/F 三态与数字格式化
├── formula/              writer.ts 公式构造：GUARD、PAR、PNT、_XFTRIGGER、_WALKGLUE、SETATREF、IFERROR
├── text/                 runs.ts 文本 run 写手：cp/pp 分段与字面换行
├── styles/               model.ts 样式表模型；writer.ts 样式表部件；connector.ts 连接线样式；fonts.ts 字体
├── masters/              client.ts 母版客户端；assets.ts 目录与记录；packer.ts 母版装配；normalize.ts 规范化；templates.ts 与 templates/ 官方模板固化
├── ports/                rows.ts 连接行读取与 ToPart 计算（100 加行号）
├── xml/                  xmlNode.ts XML 树与序列化；constants.ts 常量
└── infra/                ids.ts 形状 ID 分配；validate.ts 校验
```

边界与注意：

- common 不 import 任何 diag 包，不含图型分支；图型专用 cell 由对应 diag 包自己写；
- 母版装配是"内容原样加条目重排"：官方内容逐字保留，只重写 ID 与 rId；
- 数值格式化必须确定：同一输入两次产出的字节一致，产物才可复现；
- 样式 KEY 以官方基座为准，本项目用到的是节点家族与 class/ER/sequence
  各自官方基座。

## 六、图型包（四个，平级）

四个包都在 `source/diag/` 下，一个图型一个文件，互不 import，
对外各导出一个渲染器。

### 6.1 diag/common：flowchart 与 block

扁平图共用同一套"节点加边加簇"语义。节点按 `shapeKind` 分发到对应几何与
官方母版；边按箭头与样式选择粘附方式，钉接用 PAR，自动走线用 `_WALKGLUE`；
子图写成簇框。它也是其它图型包的参照实现。

边界：只做扁平图，不做容器与成员；`classDef` 的颜色走实例单元格覆盖，
不建独立样式表。

### 6.2 diag/class

类盒是列表容器：Group 嵌套子形状，容器上写 User 行族，行宽由
`Controls.ROW_1` 管；成员行与分隔线是页级形状，用 `DEPENDSON` 与
`LISTSHEETREF` 公式回指容器，Visio 打开时自动重排。关系线用官方
Inheritance 母版当载体，六类 mermaid 关系映射到官方母版 Actions 菜单里的
样式，只覆写箭头与线型；构造型只有 interface 有官方母版，其它标记按普通
类盒渲染并告警。

边界：类盒只写容器结构与缓存位置，自动重排交给 Visio 重算；母版按 NameU
收集后交给公用库装配，本包不碰资产。

### 6.3 diag/er

实体是数据库语义的列表容器：官方 Entity 母版加三类行母版，主键属性、
普通属性、主键分隔线；主键、外键、必填走属性行的 User 行；关系线用官方
Relationship 母版，关系名走一维线的文本。

边界：属性行只有左右两枚连接行，关系端点钉到属性行时端口要按行数容错；
`msvSDList*` 行族的写法与 class 同构，两边各自持有，不从对方导入。

### 6.4 diag/sequence

生命线用官方 Object/Actor lifeline 母版，母版自带 100 枚时间格连接行，
步长 6.35mm；消息四类母版按语义分发；激活条是带时间点行的 1-D 形状；
片段是容器加顶层操作数。生命线的页眉宽高、虚线体端点等几何显式写入，
内容外包围框由 `sequenceContentBox()` 算出来，渲染器据此做坐标映射。

边界：时间格行是母版规模，页面实例只写用到的行缓存；消息端点的行号由
布局算出后写入，不靠公式求值。

## 七、打包层

### 7.1 xml-parts：部件栈

收拢图型包产出的部件，补齐 docProps、`[Content_Types].xml`、包级与页面级
关系表，再按契约 B 校验一遍。它不画形状，只整理与检查。

边界：公共部件按最小必要填写，docProps 只写标题与生成者，`custom.xml`
带 `RecalcDocument=true`；页面级关系表按是否启用母版引用决定生成。

### 7.2 squeeze：压缩库

契约 B 到 .vsdx 字节：部件名映射成 zip 条目，写内容类型与关系表，
用固定参数压缩。它只懂 OPC/ZIP，不认识图型。

边界：DOS 时间恒 0、deflate 参数固定，保证产物字节确定；XML 文本按
UTF-8 无 BOM 编码。

## 八、适配层与接入层（alpha3）

适配层 `source/service/` 是库与命令行共用的能力面，一次会话（`ServiceSession`）
持有输出目录、工作目录与路径策略，惰性复用同一个 Chromium：

| 能力 | 入口 | 干什么 |
| --- | --- | --- |
| 转换 | `convert` | mermaid 文本到 `.vsdx`，写盘前走原子写 |
| 批量 | `convertMany` | 多项转换，带条目上限与覆盖开关 |
| 校验 | `validate` | 只解析不落盘，回报图型与结构是否可用 |
| 检视 | `inspect` | 读已有 `.vsdx`，回报部件与页面统计 |

边界与约定：

- 错误统一成 `ServiceError`，码固定为 `unsupported_kind`、`parse_error`、
  `path_denied`、`too_large`、`invalid_argument`、`renderer_unavailable`、
  `internal`，每条带可执行提示；调用方只认码，不解析文案；
- 入参上限集中在 `service/limits.ts`（输入 256KB、输出 8MB、批量 50 项），
  超限报 `too_large`，不静默截断；
- 路径一律过 `service/paths.ts` 的策略：输出必须落在允许目录内，否则 `path_denied`；
- 适配层不认协议、不认识命令行参数，也不复制转换逻辑。

接入层 `source/cli/` 把四个能力暴露给人与其他工程：子命令
`convert | validate | batch | inspect`，stdout 只出一行 JSON 回执，
stderr 出人读摘要，退出码 0 成功、1 转换失败、2 参数错误。

对外的字段、回执、错误码与退出码以 [docs/接口协议.md](../接口协议.md) 为正文，
本区不重复。

## 九、分层红线

- 图型包之间不互相 import，共同能力下沉到公用库；
- parser 只产契约 A，diag 只消费契约 A 产出契约 B，两份契约之间不共享
  其它数据结构；
- 压缩库不碰 xml 语义，公用库不掺图型判断，编排层不被任何人依赖；
- 新增图型等于新增一个 `diag/<kind>.ts` 加一行分派，不改其它图型。
