>

## 一、为什么要重做

旧实现把各种图型混在一个大目录里画图，样式、母版、几何各写各的，产物与
Visio 官方样本对不上，改一处容易碰坏另一处。重做的做法是拆成流水线：
mermaid 文本一段一段走，每一段是一个独立小包，包与包之间只通过两份契约
交换数据。

## 二、重做后的流水线

```
mermaid 文本
   │
   ▼
① parser         文字翻译成 json（一张图的内容清单）
   │
   ▼
② 四个图型包      每个图型一个包（通用/class/ER/时序，覆盖五类图型；block 走通用包）
   │              它只干一件事：把自己的 json 变成"xml 数据"
   │
   ▼
③ xml 部件栈     把各个包产出的 xml 数据聚拢、补公共部分、检查一遍
   │
   ▼
④ 压缩库         把 xml 数据打包成真正的 .vsdx 文件
```

包与契约的分工：

| 包 | 一句话职责 | 不做的事 |
| --- | --- | --- |
| parser | mermaid 文本变成契约 A | 不写任何 xml、不懂 Visio |
| 通用 / class / ER / 时序 | 各管各的图型：契约 A 变成契约 B | 不碰别的图型、不碰压缩、互不 import |
| 公用库 | 大伙共用的零件箱：形状、单元格、公式、文本、样式、端口、母版 | 不掺和任何图型判断 |
| xml 部件栈 | 收拢部件、补文档属性与登记表、整体校验 | 不画形状，只整理和检查 |
| 压缩库 | 部件数据变成 zip 字节 | 只懂打包，不懂 xml 语义 |

| 契约 | 是什么 | 从谁到谁 |
| --- | --- | --- |
| 契约 A | "画了什么"的 json 清单 | parser → 图型包 |
| 契约 B | "完整的 vsdx 内容"的部件数组 | 图型包 → 部件栈 → 压缩库 |

## 五、设计约定（重做时定的）

1. 每个包一个门面类，对外只有一个入口方法；
2. 类按职责命名：布局器只算位置，写手只拼 xml，引擎负责编排，服务提供无状态能力；
3. 纯数据用 interface 加默认工厂，不带方法；有状态对象在包内私有；
4. 依赖方向固定：引擎到布局器到写手到公用库零件；可替换的位置先定义接口；
5. 可单测的纯函数不读文件、不开浏览器、不进全局。

命名与代码风格见 `docs/AI开发约定/代码规范.md`，本项目的结构约定见
`docs/AI开发约定/项目特定规范.md`。
