# 00 一页看懂：本次重构是什么

> 本文件用大白话讲清楚整个重构。你看完这一页就懂了一半；剩下的一半
> 在各包的详细设计里，按图索骥即可。所有包的详细文档见 README 文档树。

## 一句话

把现在"一个大目录里混着画图"的代码，改成**流水线**：mermaid 文本
→ 一块一块地走 → 最后出 .vsdx。每一段是一个独立小包，互相只通过
两份"契约"交换数据。

## 五步流水线

```
mermaid 文本
   │
   ▼
① parser         文字翻译成 json（一张图的内容清单）
   │
   ▼
② 五个图型包      每个图型一个包（通用/class/ER/时序；block 走通用包）
   │              它只干一件事：把自己的 json 变成"xml 数据"
   │
   ▼
③ xml 部件栈     把各个包产出的 xml 数据聚拢、补公共部分、检查一遍
   │
   ▼
④ 压缩库         把 xml 数据打包成真正的 .vsdx 文件
```

## 每个包是谁、干什么、不管什么

| 包 | 一句话职责 | 它不做的事（边界） |
| --- | --- | --- |
| parser | 把 mermaid 文本变成 json 清单 | 不写任何 xml、不懂 Visio |
| 通用/class/ER/时序 | 各管各的图型：json → xml 数据（flowchart/block 走通用包） | 不碰别的图型；不碰压缩；不互相调用 |
| 公用库 | 大伙共用的"零件工具箱"：画形状、写单元格、公式、样式、端口、母版 | 不掺和任何图型判断 |
| xml 部件栈 | 收拢部件、补文档属性/登记表/关系表、整体校验 | 不画形状，只整理和检查 |
| 压缩库 | 部件数据 → zip 字节 | 只懂打包，不懂 xml 语义 |

## 两份契约（包与包之间只认它们）

| 契约 | 是什么 | 从谁到谁 |
| --- | --- | --- |
| 契约 A | "画了什么"的 json 清单 | parser → 图型包 |
| 契约 B | "完整的 vsdx 内容"的部件数组 | 图型包 → 部件栈 → 压缩库 |

## 类图思想怎么体现

虽然 JS 没那么严格，但设计遵循面向对象的三条：

1. 每个包一个"门面类"，外面只能看到它的一个入口方法；
2. 类按职责分：布局器（算位置）、写手（拼 xml）、服务（只提供能力）；
3. 纯数据永远是 interface：谁能读、谁能写，写死在契约里。

各包的类与函数清单见 `04-转义层/` 下的对应文档；类图与工作流程图的图形版
见 `diagrams/` 目录（Mermaid 格式，可在 Mermaid Live Editor 打开）。
