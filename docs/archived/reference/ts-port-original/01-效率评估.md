# 01 — TS 化效率评估：效率是否会下降？

> 问题："把 mmd2vsdx 做成整体 TS 生态实现，效率是否会下降？"
> 本文把"效率"拆成五个维度分别评估，给出结论、数据依据与对策。
> 结论先行：**不会下降**——在正确的使用形态下持平或更好；开发与维护效率显著提升。

---

## 1. 评估框架：效率的五个维度

| 维度 | 含义 | 结论 |
|---|---|---|
| 运行性能 | 单次转换端到端耗时、吞吐 | 持平或更好（瓶颈不在语言） |
| 内存占用 | 峰值内存、常驻内存 | 基线略高，对本负载无影响 |
| 启动时间 | CLI 单次冷启动 | 变慢（Node + 浏览器拉起），可化解 |
| 开发效率 | 编码/联调/迭代速度 | 显著提升 |
| 维护与生态 | 依赖、构建、分发、跨平台、集成 | 显著提升 |

---

## 2. 运行性能：瓶颈在哪里？（关键论证）

### 2.1 现状端到端耗时构成（单图，实测经验值）

```
总耗时 ≈ 浏览器渲染（0.5–2s，占比 90%+）
       + 提取（DOM 解析，~10–50ms）
       + HTTP 往返 + 子进程通信（~1–10ms）
       + JSON 解析（~1ms）
       + IR 翻译 + XML 构建（~5–50ms，图越大越慢）
       + ZIP 打包（~5–50ms）
```

**决定性事实：瓶颈是 Chromium 渲染 Mermaid（mermaid 布局算法），与实现语言无关。**
C++ 引擎与 Node 引擎在这条链上都是"配角"。

### 2.2 TS 化后各部分对比

| 环节 | C++ 现状 | TS 化后 | 对比 |
|---|---|---|---|
| Mermaid 渲染 | Chromium（Playwright，Node 子进程） | 同样 Chromium（Playwright）或 mermaid 同构渲染 | **不变**（瓶颈保持） |
| 提取（extract/*.mjs） | 浏览器页面内 JS | 原样保留 | 不变 |
| 编排通信 | 子进程拉起 + HTTP 往返 + ready 行解析 + 崩溃重启 | 进程内直调（模块函数调用） | **省掉 5–20ms/图 + 全部进程管理代码** |
| JSON 解析 | nlohmann::json | `JSON.parse`（V8 原生） | Node 更快 |
| IR 翻译 | 手写字段映射 | 同逻辑 TS | 相当 |
| XML 构建 | libxml2 树 + 手写 XmlBuilder | 自研轻量 XML 树/序列化器（或 fast-xml-parser） | 相当（字符串拼接为主，V8 不慢） |
| ZIP 打包 | 自研 ZipArchive（644 行，zlib deflate） | `node:zlib`（C++ 原生 deflate）+ 自研 ZIP 封装 | **相当**（底层同为 zlib） |
| HTTP server（服务形态） | 自研 HttpServer（WinHTTP） | `node:http`（libuv 原生） | Node 更快、更稳 |

### 2.3 结论（运行性能）

- **单图端到端**：`≈ 浏览器渲染耗时`（不变）+ `若干 ms`（TS 更少）。
  持平或略快。
- **批量转换**：瓶颈在串行浏览器渲染队列（mermaid-snapshot 已是串行）。
  TS 化后可选做**多浏览器上下文/多 worker 并行**（C++ 现状是严格串行单例，
  TS 化反而获得并行能力），吞吐可提升。
- **服务形态**：每请求省去跨进程协议开销，且不再有"服务崩溃自动重启"的
  维护路径（同进程异常直接可查）。
- **极端大图**（数千节点）：XML 树构建与 ZIP 为线性成本，Node 侧与 C++
  同数量级（< 2×），仍远小于渲染时间。

## 3. 内存占用

| 项 | C++ | Node/TS | 影响 |
|---|---|---|---|
| 常驻基线 | ~5–15MB | ~40–80MB | 无感（现代机器） |
| 单图峰值 | 图大小 × ~10–50 | 图大小 × ~20–80（V8 对象开销） | 单图 ≤ 几 MB，峰值 < 200MB，无感 |
| 浏览器 | Chromium ~300–500MB（两者相同） | 相同 | 不变 |

**结论：内存不构成问题。** 唯一注意点：批量转换时避免持有全部结果，
流式写出（现状已是逐文件写出，保持即可）。

---

## 4. 启动时间（唯一真实变慢的维度）

| 形态 | C++ | TS | 差异 |
|---|---|---|---|
| 常驻服务 | 冷启动 ~10ms，之后每图快 | Node 冷启动 ~100–300ms，之后每图快 | 一次性 ~0.3s，无感 |
| 批量转换 | 冷启动 ~10ms | Node ~0.2s + Chromium 拉起 ~1–2s | 一次性 ~2s，无感 |
| CLI 单文件 | ~10ms + Chromium 拉起 | ~0.2s + Chromium 拉起 | **每调一次多 ~0.2s**，唯一明显项 |

**对策（按推荐序）：**
1. **服务形态为主**：TS 化后 `serve` 是天然首选（Node 本身就是常驻进程），
   CLI 包装为对服务的一次调用或同一进程内直调（进程内直调 + 浏览器预热后
   单文件转换可做到 ~1s 内）。
2. **浏览器预热**：启动后立即渲染一次小图（现状已有 warmup，保留）。
3. **按需拉起**：CLI 单文件场景可接受 ~1.5–2s 总量（mermaid 渲染本身 ~0.5–1s）。

## 5. 开发效率：提升点清单

| # | 提升点 | 说明 |
|---|---|---|
| 1 | 单语言单生态 | 消灭 C++/JS 双栈：不再需要 CMake、MSVC、libxml2/zlib/nlohmann/doctest 外挂安装与 find_package 配置 |
| 2 | 跨进程协议 → 编译期类型 | snapshot JSON 协议从"文档约定"升级为 TS interface（提取层与转换层同库共享），枚举/字段错误编译期暴露 |
| 3 | 免 FFI/免句柄 | 消灭 WinHTTP、Windows 进程句柄、libxml2 节点指针、OLE 相关 C 指针代码 |
| 4 | 测试一体 | doctest → vitest；8 套测试同一生态，可增量 watch 运行 |
| 5 | 类型即文档 | IR/契约类型（core）用 TS interface + 注释，IDE 全链路跳转 |
| 6 | 工具链统一 | tsc/tsup/vitest/eslint 一套；`npm run build && npm test` 即可验证 |
| 7 | 跨平台免费 | 现状 Windows-only（WinHTTP/进程 API），TS 化后 macOS/Linux 立即可用（Linux 移植方案文档作废） |
| 8 | 可嵌入任意宿主 | 浏览器/Worker/Electron/服务端皆可：包内零平台依赖（除 Playwright） |
| 9 | 分发 | npm 包（CLI + 库 API + serve），`npx mmd2vsdx` 可用；告别编译分发 |

**效率账**：业务代码 ≈ 13,000 行（剔除生成资源），TS 平移预计 **9,000–11,000 行**
（类型收编 + 无重复头文件/实现分离）。C++ 的 .hpp/.cpp 双写、模板样板、
内存管理代码在 TS 中全部消失。

## 6. 维护与生态：提升点清单

| 项 | C++ 现状 | TS 化后 |
|---|---|---|
| 依赖 | 4 编译期外挂库 + WinHTTP + 平台 API | mermaid/playwright（已有）+ 少量纯 JS 工具（zod 可选） |
| 构建 | CMake 双配置（Debug/Release）+ 外挂路径 | `tsc` 一条命令 |
| 测试 | ctest + 手工 bat | vitest watch |
| 资源生成 | extract_stencil.py（独立脚本） | 生成式 TS 资产脚本（ts 或保留 py 均可） |
| 平台 | Windows only（有 Linux 方案但未实施） | 全平台 |
| 第三方升级 | mermaid 升级只影响 snapshot | 同样，仅一处依赖版本 |
| 新人上手 | 需装 VS + CMake + 4 个库 | `npm install && npm test` |

## 7. 风险与成本（诚实清单）

| 风险 | 影响 | 对策 |
|---|---|---|
| 数字格式化差异 | 产物 XML 中浮点字符串与 C++ `%g`/fixed 输出不同，导致字节级差异 | 明确"语义等价"为验收标准（Visio 只认数值），不追求字节一致；关键处对照 C++ 格式规则移植（见 04） |
| XML 转义/编码 | libxml2 自动处理转义；TS 需自管（& < > " ' 与 UTF-8/UTF-16） | 统一 escape 工具 + 单测覆盖；文本全 ASCII 样本 + 中文样本双验证 |
| 模具资源分发合规 | stencilresources 嵌入官方模具（仅自用）；TS 化后 npm 分发需谨慎 | 资源生成脚本保留；npm 包默认**不带**模具，提供 `prepare-stencils` 命令由用户从本机 Visio 提取（与现状红线一致） |
| Playwright 依赖体积 | npm 包含浏览器下载策略 | 按现状：`npx playwright install chromium` 可选安装；包本身只依赖 playwright 库 |
| 行为漂移 | 平移过程引入逻辑差异 | 金标准：16 样本产物结构对比（复用 compare_gantt.py 思路做 TS 版校验器）+ roundtrip 测试 |
| 工期 | ≈13,000 行业务代码 + 1,593 行 JS 收编 | 按 03 里程碑分 6 阶段，每阶段可独立交付验证 |

---

## 8. 效率评估总结

```
运行性能   ██████████  持平或更好（瓶颈=浏览器渲染，与语言无关；省掉跨进程开销）
内存       █████████░  略高但无影响（单图负载远小于基线）
启动       ██████░░░░  变慢（Node ~0.2s），服务/批量形态无感，CLI 可预热
开发效率   ██████████  显著提升（单语言、类型化协议、免四库免平台 API）
维护生态   ██████████  显著提升（npm 分发、全平台、单工具链）
```

**最终结论：效率不会下降。** TS 化在运行时维度与 C++ 持平或略优，
在开发与维护维度全面占优；唯一代价（CLI 冷启动 +~0.2s）通过
"服务/批量为主、预热兜底"的形态设计完全化解。

**建议的实施前置条件**（进入 02 需求规格前确认）：
1. 接受"语义等价"而非"字节等价"作为产物验收标准；
2. 接受 npm 包默认不含官方模具、由用户侧脚本提取的分发红线；
3. 确认主使用形态（服务 / 批量 / CLI 三选一为主，其余兼容）。
