# 02 · 坑位与解法（class / ER / sequence 实战）

> 每条格式：**现象 → 根因 → 正解 → 证据**。
> 标注 `[class]` `[er]` `[通用]` 表示来源；数值均为官方样本实测值。
> 相关源码：`source/common/styles/writer.ts`、`source/diag/class.ts`、
> `source/diag/er.ts`、`source/parser/ext/*.mjs`、`tests/spec.test.ts`。

## 1. 样式与文档基座

### 1.1 [class/er] 母版样式引用落空 → 黑填充

- **现象**：关系线/形状填充变黑、样式错乱。
- **根因**：母版写 `LineStyle='7' FillStyle='7' TextStyle='7'`，指向**官方
  Connector 样式（ID7）**；而旧实现用合成 `document.xml`：Connector 在 **ID5**、
  且**缺 Theme（ID6）**，母版的 `THEMEVAL()/THEMEPROP()` 公式全部失效。
- **正解**：class/er 分支改用**官方 `document.xml` 基座 verbatim**：
  - `writer.ts` 常量 `kOfficialDocumentBody`（class-all-in-one）、
    `kOfficialErDocumentBody`（er-all-in-one）；
  - `buildOfficialDocumentPart()` / `buildOfficialErDocumentPart()`；
  - `convert.ts` 按 `a.kind` 选择基座，其它图型保持合成 + 注入 Connector。
- **证据**：官方基座 `StyleSheets: 0=No Style | 1=Text Only | 2=None |
  3=Normal | 4=Guide | **6=Theme** | **7=Connector**`；ER 关系母版
  `LineStyle=7 FillStyle=7`。提交 `364e5aa`、`c255cc9`。

### 1.2 [class/er] 模板包选错（旧图型包 vs all-in-one）

- **现象**：缺线型母版、母版 ID 对不上官方实例、带无用的通用件。
- **根因**：早期按旧图型包（`class/`、`ER/`）装配模板。
- **正解**：一律用 all-in-one 包；class = `class ∪ class-all-in-one`，
  ER = `er-all-in-one`（5 枚）。详见 [01 对齐方法](01-官方模板对齐方法.md) 第 1 步。
- **证据**：官方实例 `Master="2/4/5/6/7"` 对应 er-all-in-one 的
  Entity/PKAttr/PKSep/Attr/Relationship；旧 ER 包是 7/8/9/10/11。

### 1.3 [通用] 官方 XML 用单引号，审计脚本别只认双引号

- **现象**：`temp/verify-vsdx.mjs` 把 class/er 产物误判为 BAD（"0 号 No Style 空壳"）。
- **根因**：脚本正则写死 `<StyleSheet ID="0"`，而官方基座是单引号
  `<StyleSheet ID='0'`，匹配失败 → 取到空串。
- **正解**：审计正则兼容 `['"]`；`verify-vsdx.mjs` 已修，全量通过
  （当时 16/16；图型收敛后为 9/9）。
- **教训**：凡是解析**官方原文**的地方，引号风格必须容错。

## 2. 实例代数

### 2.1 [通用] 段覆写必须写 `IX='0'`

- **现象**：形状"多画一段线/多一圈矩形"。
- **根因**：母版 `Geometry` 段带 `IX='0'`；实例不写 `IX` 会被 Visio 当作
  **新增段**（自动编号 1），母版段保留 → 双几何段。
- **正解**：所有 Geometry 段显式 `IX='0'`（`section(name, rows, '0')`）。
  `Connection/User/Character` 段官方实例**不写 IX**。
- **证据**：官方实例 `<Section N="Geometry" IX="0">`（entity/PK 行/分隔线/关系线
  全部如此）；`source/diag/class.ts`、`source/diag/er.ts` 的 `section()` 已带 ix 参数。

### 2.2 [通用] 单位语义：V 是英寸，`U='MM'` 只是标签

- **现象**：数值看起来是 MM，实际按 MM 写会错 25.4 倍。
- **根因**：Visio 单元格内部值恒为英寸；`U` 仅影响显示。
- **正解**：写 `V=<英寸值>`，`U='MM'` 原样照抄母版标签（如需保真）。
- **证据**：ER 属性行 `Width V=2.559055118110236 U=MM`（=65MM 的英寸值）；
  子形状 `PinY=-0.1272443539239158(MM)` 实际是 -0.127 英寸。

### 2.3 [class] 关系线代数（官方逐值）

- **现象**：连接线悬空、箭角位置不对、线数不全。
- **根因**：用自创常数近似官方实例代数。
- **正解**（class-all-in-one）：
  - `Width=GUARD(EndX-BeginX)`、`Height=GUARD(EndY-BeginY)`（**带符号**）；
  - `Pin=端点中点`、`LocPin=W/2,H/2`；
  - 几何 Z 转折 = 距 Begin 端口出线侧 `0.2452500075101858`；
  - 端口出线侧决定转折符号（X1 右缘出线向左、X2 左缘出线向右 …）；
  - 子形状 MS6/7（Begin 对）、MS8/9（End 对）按方向角旋转 ∓45°/±135°；
    `LocPin` 常量 `0.1667217539296875`（MS6）/ `0.1333828247070313`（MS8）；
  - User 行族 `DXBegin/DYBegin/DXEnd/DYEnd/BeginAngle/EndAngle` 用官方公式。
- **证据**：官方实例 ID=55/56/66/71/76 逐值；提交 `364e5aa`。

### 2.4 [er] 关系线代数（官方逐值）

- **现象**：关系线走线形状/端标记/标签位置不对。
- **正解**（er-all-in-one）：
  - `W=GUARD(EndX-BeginX)`、`H=GUARD(EndY-BeginY)`（带符号）；
  - 几何 **L 形** `(0,0)→(0,H)→(W,H)`（实例覆写 `LineTo IX=2` 的 Y、`IX=3` 的 X/Y）；
  - `Connection IX0=(0,DYBegin)`、`IX1=(W-DXEnd,H)`（本地吸着位，驱动母版
    `DXBegin/DYBegin/DXEnd/DYEnd/BeginAngle/EndAngle` 公式）；
  - 端标记子形状 **6..9**：`PinY/PinX = Con + cos/sin(角度±45°/±135°)×2.5MM`，
    `2.5MM=0.09842519685039369`、`2.5MM×sin45°=0.06959712413253433`；
  - 端从右向左（endAngle=π）时补 `LocPin` 缓存与 `EndAngle`（官方 #49 模式）；
  - 标签位 = L 形折线中点：`(|W|-|H|)/2×sign(W)`、`TxtPinY=H`；
  - 识别/非识别 → `User.Identifying`（母版 `LinePattern=GUARD(IF(Identifying,1,2))`）。
- **证据**：官方实例 #15（W=+2.2638,H=-1.5794）与 #49（W=-1.7717,H=-0.9444）逐值；
  提交 `c255cc9`。

### 2.5 [er] 实体容器：高度公式与行堆叠

- **现象**：字段高度与容器盒不匹配、分隔线占整行。
- **正解**：
  - `Height = HdrHgt + 属性行数 × rowH`，其中
    `HdrHgt=0.4361626369900174`、`rowH=0.388939397515191`；
  - **主键分隔线是 0 高行，不占槽位**；
  - 行与行**紧贴堆叠**：首行中心 = 盒顶 − HdrHgt − rowH/2；属性→属性 = rowH；
    属性→分隔线 = rowH/2；分隔线→属性 = rowH/2；
  - 实体实例**无根 Geometry 段**（边框由嵌套子形状 #6 承载，自写根段会多画一圈）。
- **证据**：官方实体 #1（3 属性+分隔线）H=1.602981、行位
  0.630632/0.825102/1.019572/1.408511；#21/#35 同规则。提交 `c255cc9`。

### 2.6 [er] 成员行的最小差异

- **现象**：多余的 Character/Paragraph/Color 段导致样式异常。
- **正解**：
  - 属性行 Cells：`PinX/PinY/Width(MM,F)/LocPinX(MM,Inh)/Relationships/ShapeFixedCode/TxtWidth(MM,Inh)`；
    **不写 Height、不写 ObjType**；
  - User 单段：`ContainerMargin / WidthMin / [普通行颜色四行] / ItemIndex`；
  - 普通行在 Connection **前**有 1 枚 `Character(Color=0 Inh)`，**几何后没有第二枚**；
  - 子形状：**PK 行为空引用** `<Shape ID="6" Type="Shape" MasterShape="6"/>`；
    普通行子形状仅带 `Section Character(Color=0 Inh)`（无 Cell Color）。
- **证据**：官方 #5（PK 行）与 #9（普通行）原文；提交 `c255cc9`。

## 3. 容器与布局

### 3.1 [class] mmd 布局保比例

- **现象**：自创网格布局与 mermaid 预览差异大、连接线交叉。
- **正解**：从 SVG 提取实体/类的中心与尺寸 → 按行聚簇（容差 48px）+ 比例间距
  重排；行高/盒宽仍用官方公式（避免行高不一致时重叠）；无 mmd 布局时回退旧布局。
- **证据**：`source/parser/ext/class.mjs`、`source/diag/class.ts` `clusterAxis()`；
  提交 `364e5aa`。

### 3.2 [er] 边选择与端口

- **正解**：从关系 path 的起终点与实体盒的最近边判定 `fromEdge/toEdge`
  （left/right/top/bottom）；渲染端取**边中点**（官方端口 X1 左 / X2 右 /
  X3 下 / X4 上，`ToPart=100+IX`），不用 mmd 角点。
- **证据**：`source/parser/ext/er.mjs` `edgeOf()/extractEdges()`；提交 `c255cc9`。

### 3.3 [er] 同行实体高度不同时，`top/bottom` 必须取自身盒

- **现象**：只有"1 主键 + 1 普通属性"的实体，主键与成员行整体上移、压住表名。
- **根因**：mmd 布局中同一行实体共享行高 `hRow`（行内取最大），但布局把每个
  实体的 `top/bottom` 写成了**行顶/行底**。矮实体（2 属性）的行组因此按行顶起算
  → 整体抬高半行，首行正好落在表名上。
- **正解**：`bb.top = yBase + bb.h/2`、`bb.bottom = yBase - bb.h/2`（**各实体自身盒**）。
- **证据**：修复后 ORDER（2 属性）H=1.214041、行位 0.630632/0.825102/1.019572，
  与 3 属性实体同模式；Visio COM 打开确认逐值保留。提交 `c255cc9`。

### 3.4 [教训] 别用"拉平参数"掩盖症状

- **经过**：为修 3.3 的症状，曾把高度改成 `HdrHgt + max(属性数,3)×rowH`
  （让所有实体等高），症状消失——但代价是**盒子不再贴合内容**，用户随即发现
  "高度不随属性数变化"。
- **根因**：真正的问题是布局取错了盒顶，等高只是让错误不再显形。
- **正解**：定位到取错的值（3.3），恢复动态高度。
- **教训**：**症状消失 ≠ 问题解决**。当"补丁"同时改变了无关参数（把所有盒子拉平），
  优先怀疑它只是在掩盖错误；用 Visio 实测对照写入值，能直接分辨
  "Visio 改的" vs "我们写错的"。
- **关联误判**：过程中还把官方 #21 误判为"2 属性实体有 3 行下限"——实际是
  解析正则截断漏了成员 #32（见 4.1），官方 #21 其实是 **3 属性**、高度精确贴合。

## 4. 解析与审计（工具坑）

### 4.1 [通用] 非贪婪正则会在嵌套括号处静默截断

- **现象**：统计官方实体的 `DEPENDSON(2,…)` 成员时少算最后一个。
- **根因**：`SUM\(DEPENDSON\(2,([\s\S]*?)\)\)` 在 `Sheet.32!SheetRef()` 的
  `()` 处遇到第一个 `))` 就停，末尾成员被截成 `SheetRef(`，计数少 1。
- **正解**：计数用 `Sheet\.(\d+)!SheetRef`（不要求后续括号），或用深度感知解析。
- **代价**：曾据此得出"官方 2 属性实体高度含 3 行槽位"的错误结论，写了错误补丁
  （提交 `c255cc9`）。
- **教训**：**验证性脚本的解析错误会直接污染结论**。凡用于"定规则"的统计，
  先打印原始片段人工核对一遍。

### 4.2 [通用] 自闭合空形状必须单独处理

- **现象**：`tests/spec.test.ts` 里属性行统计 13 ≠ 实际 21（差 8 个 PK 行）。
- **根因**：官方/我们的空子形状序列化为 `<Shape ID="6" MasterShape="6"/>`；
  栈式解析把自闭合标签当**开标签**入栈，后续 `</Shape>` 错位、body 被截断。
- **正解**：`parseAllShapes` 识别 `/\/$/` 的自闭合，直接成条目不入栈。
- **证据**：`tests/spec.test.ts` `parseAllShapes()`；提交 `c255cc9`。

### 4.3 [通用] 审计断言要表达官方语义

- **反例**："实体 Height 存在且不为某个值"这种断言永远为真，等于没写。
- **正解**：断言公式本身——`H = 0.4361626369900174 + n×0.388939397515191`
  （`n` 由成员解析得出）、行堆叠步进、`W=GUARD(EndX-BeginX)`、`IX='0'`、
  端标记 6..9、端口 `ToPart=100+IX`。
- **收益**：改错公式立刻红灯；本轮多次靠它挡住回归。

## 5. mmd（mermaid）提取

### 5.1 [通用] SVG 结构因图型而异

| 图型 | 分组 transform | id 形如 |
| --- | --- | --- |
| class | `translate(中心x,中心y)` | `classId-<名>-<序号>` |
| er | `translate(左上x,左上y )`（**注意右括号前有空格**） | `entity-<净化名>-<uuid>` |

- **正解**：`/translate\(([-\d.]+)[,\s]+([-\d.]+)\s*\)/` 容错空格；
  ER 的中心 = 左上 + 尺寸/2。
- **证据**：`source/parser/ext/er.mjs`；提交 `c255cc9`。

### 5.2 [er] id 净化后要回映真实名

- **现象**：`ORDER_LINE` 的布局取不到。
- **根因**：mermaid `BAD_ID_CHARS_REGEXP=/[^\dA-Za-z](\W)*/g` 会剥掉下划线
  （`ORDER_LINE → ORDERLINE`），布局 key 与实体名不一致。
- **正解**：在提取器里复刻净化规则，用 DB 实体名建 `sanitized → 真实名` 映射。
- **证据**：`source/parser/ext/er.mjs` `sanitize()/bySan`。

### 5.3 [通用] 提取失败必须可降级

- 布局/边提取全部包 `try/catch` 并返回空，渲染端 `hasMmd` 判定失败即回退旧布局。
- 好处：解析器版本差异或结构变化时，产物仍可用，只是少了比例保真。

### 5.4 [通用] 边路径容器因图型而异，漏选会整批丢线

- **现象**：block 图（`block-beta`）转出来一个连线都没有，连 `Dynamic connector`
  母版都不在册；flowchart 同输入正常。
- **根因**：边路径的父容器不同——flowchart 在 `g.edgePaths` 下，**block 直接挂在
  `g.block` 下**。提取器只选 `.edgePaths path`，block 的边一条都选不到。
- **正解**：选择器取 `.edgePaths path, g.block > path.flowchart-link` 并按元素去重。
- **证据**：`source/parser/ext/generic.mjs`；最小复现 `block-beta` 带箭头从 0 条
  变 2~3 条连线（提交 `84e3239`）。

### 5.5 [通用] 边 id 的字符集必须与节点 id 同口径

- **现象**：节点 id 用中文时整图丢连线（形状数 = 节点数），标签用中文则正常。
- **根因**：节点侧 `nodeId()` 用 `(.+)` 取任意字符，边侧 `edgeIds()` 却按
  `[A-Za-z0-9_]+` ASCII 白名单匹配 → 解析不出 from/to 就 `return null`，整条边丢掉。
- **正解**：**用本轮已解析出的节点 id 集合去切分边 id**（先试 `id` 属性再试 `class`），
  天然兼容中文、兼容 id 里自带 `-`，也顺带吃掉 block 的 `1-A-B` 序号前缀与
  flowchart 的 `-0` 索引后缀；ASCII 正则降级为回退路径。
- **证据**：`source/parser/ext/generic.mjs`；6 个用例（block/flowchart × ASCII/中文/
  混用）全部出连线，既有 ASCII 样本产物逐字节未变（提交 `a4a2f93`）。

### 5.6 [通用] 路径取点正则要支持负号与曲线段

- **现象**：block 的边即使被选中，`waypoints` 也只有 0~1 个点。
- **根因**：`d` 里坐标可带负号（block 的边整条在负坐标区），旧正则用 `[\d.]+` 匹配不到；
  且 block 的边是三次曲线 `C` 而不是 `L`，只认 `M/L` 会漏掉端点。
- **正解**：按段类型取点——`M/L/H/V` 端点全取，`C/S/Q/T` 只取段末端（控制点不在线上），
  支持相对命令与 `Z`，并去掉连续重复点。
- **证据**：`source/parser/ext/generic.mjs`；block 边从 0~1 点变 5 点。

## 6. 验证与工程流程

### 6.0 [通用] 父形状 ID 分配必须先自增

- **现象**：产物在 Visio 打开时**直接崩溃**（RPC 0x800706BE）。
- **根因**：`const id = ctx.nextId;` 忘记自增，随后子形状 `ctx.nextId++` 先取到了同一个 ID
  → 父子 ID 重复。
- **正解**：`const id = ctx.nextId++;`（父先占号，子形状顺延）。
- **教训**：ID 分配函数化（`pushShape(ctx, el, id)`）并保持"先占号后写子"的固定顺序。

### 6.1 [通用] Visio COM 当渲染真值

- 打开产物 → 读 `CellsU('Height').ResultIU` / `PinY` → 与写入值比对；
  可另导出 PNG 存档。
- 判定表：

| 观察 | 结论 |
| --- | --- |
| Visio 值与写入一致 | 我们写对了，Visio 不干预 |
| Visio 值被改（重排/覆盖） | 要么触发容器行为，要么我们写错 |
| 两者都"看起来对"但用户说不对 | 大概率是**布局/相对位置**错，不是单值错（3.3 即此类） |

- 细节与脚本见 [03-工具与脚本手册.md](03-工具与脚本手册.md) 第 1 节。

### 6.2 [通用] 产物被 Visio 占用会 EBUSY

- **现象**：`batch-convert` 报 `EBUSY: resource busy or locked`。
- **正解**：先复制到 `temp/` 再打开；需要重新生成正式产物时让用户关闭 Visio，
  或换临时文件名（**别长期引入新名字**，用户明确要求过）。
- **附带**：探针脚本结束务必 `$doc.Close()`/`$visio.Quit()`，否则残留
  VISIO 进程锁住文件（可 `Get-Process VISIO | Stop-Process -Force` 清理）。

### 6.3 [通用] 测试基线随语义更新，而不是"改到能过"

- 每次对齐官方语义后，同步更新 `tests/master-templates.test.ts`（官方包引用）
  与 `tests/spec.test.ts`（审计断言），让测试成为**官方语义的守门人**。

### 6.4 [通用] 未推送提交按"大事件"合并

- 方法：备份分支 `backup/pre-*` → `git reset --soft origin/master` →
  用各组末尾提交的树 `git read-tree` + `git commit` 重建（保持每组末态快照）。
- 验证：`git diff <旧HEAD> HEAD` 必须为空（内容零变化）。
- 本轮重整的落地形式：整个本地历史按大事件重建成 14 笔，`v0.1-alpha1` 与
  `v0.1-alpha2` 两个 tag 重建到对应事件提交，重建前后最终树逐字节一致。

### 6.5 [环境] GitHub 直连被 DNS 劫持时的推送绕行

- **现象**：`github.com` 被解析到不可达节点（443 超时），而 `api.github.com`

## 7. 时序图（sequence）

> 官方包：`docs/VSDX解压结构研究/标准研究模板-手动创建vsdx并解压/seq-all-in-one/`（12 枚时序专用件）
> ∪ `sequence/`（旧包补 `Rectangle`/`Dynamic connector` 两枚通用件）= **14 枚**。
> 官方实例逐值来源：页面 #1/#6/#11（生命线）、#19/#20/#21/#25/#26（激活）、
> #27/#28/#30/#32（消息，含 #30 自消息）、#16/#22（片段）、#18/#20/#21（alt 容器 + 操作数）。

### 7.1 [sequence] 生命线实例必须写出嵌套子形状 MS6..9

- **现象**：产物在 Visio 里只剩 1 个形状，其余"消失"或被并入第一个形状；
  另存后可看到形状被嵌套进生命线组（顶层 7 → 1）。
- **根因**：官方生命线实例带 4 个子形状（MS6/7 空引用、MS8 单 PinY、MS9 虚线主体，
  ID 紧邻父形状）。我们不写时，Visio 打开会**现场实例化母版子形状**并分配 ID，
  与页面其它顶层形状的 ID 冲突 → 形状被误并入组/丢失。
- **正解**：按官方写出 MS6..9（父 ID 先占号，子 ID 顺延）。
- **证据**：`source/diag/sequence.ts` `writeLifeline()`；官方树
  `#1 → #2..#5`、`#6 → #7..#10`、`#11 → #12..#15`。

### 7.2 [sequence] Visio 公式的 `Connections.Xk` 是 1-based

- **现象**：消息的 `BeginX` 钉接公式被 Visio 替换成母版默认值（线跑到奇怪位置），
  而另一些消息正常。
- **根因**：我们钉到 `Connections.X0`——**X0 无效**（公式行号从 1 起，
  X1 对应存储行 IX=0）。失效的钉接会被 Visio 丢弃并回退母版默认几何。
- **正解**：存储行号 `r`（0-based）↔ 公式行号 `r+1`；`Connects` 的
  `ToCell=Connections.X{r+1}`、`ToPart=100+r`。
- **证据**：官方 #27 钉 `X4` ↔ 其 BeginY 等于行 IX=3 的 Y（`-(3+1)*0.25`）。

### 7.3 [sequence] 时间格 = 0.25IN 网格（不是自定行距）

- **正解**：母版 Connection 公式 `Y = IF(Controls.Row_1.Y < -(k+1)*6.35MM, -(k+1)*6.35MM, …)`
  → 行 IX=k 的本地 Y = `-(k+1)*0.25IN`；`Controls.Row_1.Y = -长度` 控制钳制。
  生命线本地原点（页眉底）页面 Y = 首行页面 Y + 0.25IN；`PinY = 原点 + HdrHgt/2`。
- **常量**：`HdrHgt=0.3543307086614173`、行距 `0.25`、消息半高 `0.09842519685039353`。
- **证据**：官方生命线 86 行缓存（IX=14 → -3.75IN …）与母版公式一致。

### 7.4 [sequence] 消息双 Geometry 段与 Return 符号

- **正解**（官方四类逐值）：
  - 主线 `Geometry IX=0`：`MoveTo IX=1 (Y=±2.5MM)` + `LineTo IX=2 (X=W, Y=±2.5MM)`；
  - 箭头 `Geometry IX=1`：`LineTo IX=2/3 (X=W+0.25IN)` + `LineTo IX=4 (X=W)`
    （Return 的箭头段带 `MoveTo IX=1`）；
  - `Return`：`Width/Height` 为**负**（`GUARD(-0.19685039370079DL)`）、
    `LocPinY`、几何 Y 均为负；`Control.TextPosition` 按类型给 X/Y
    （Message/Async 仅 X、Return X+Y、Self 仅 Y）。
- **注意**：Visio 打开时会按形状朝向把 Height 符号规范化（显示 `GUARD(±0.2 in)`）——
  与官方实例同样处理，视觉一致，不必对抗。

### 7.5 [sequence] 激活条与片段

- **激活条**：`Width = 时间跨度`（1-D 形状本地 X 沿页面竖直，母版公式
  `SQRT((EndX-BeginX)^2+(EndY-BeginY)^2)`）、`Height = 3MM`（厚度，继承）；
  Connection 行沿跨度每 0.25IN 一对（`X = span - j*0.25`，Y 交替 0/Height）。
  `Begin` 在下端（较晚行）、`End` 在上端（较早行）。
- **片段**：根 `Geometry IX=0`（`LineTo IX=2/3 X=Width`）+ 子形状
  MS6（关键词带，`PinX/Width/LocPinX`，继承母版文字）与 MS7（参数带，写标签）；
  实例写 `Height/LocPinY` 才能包住循环体（官方样本未写、沿用母版默认 50MM）。

### 7.6 [sequence] 片段包围盒别把"空参与者"标记算进去

- **现象**：循环片段左边界被拖到页面外（实测 x=-0.4166IN），右边与高度正常。
- **根因**：计算片段包围盒时遍历区间内所有消息，而 `loop`/`loopend` 标记行的
  `from`/`to` 为空 → 查参与者坐标得到 0 → `xMin=0`，再减 40px 边距 → 左边界跑到负值。
- **正解**：只统计能解析出参与者坐标的消息（`typeof actorX[id] === 'number'`），
  标记行跳过。
- **证据**：`source/parser/ext/sequence.mjs` 片段分支；修复后 loop 片段
  中心 1.8229、宽 2.9167（=[Alice-40px, Bob+40px]）。

### 7.7 [sequence] 消息文字被线"压住" = 文档基座缺 ID7 Connector 白底

- **现象**：连接线标签看起来在线下面（线穿过文字），位置本身没错。
- **根因**：消息/激活母版引用 `LineStyle='7'`（官方 Connector），其
  `TextBkgnd='#ffffff'` 正是"文字白底遮住线"的机制；而 sequence 原先用合成
  文档基座（Connector 注入在 ID5）→ 母版引用落空 → 文字没有白底，线直接压在字上。
  这与 class/er 的"黑填充"是同一条坑（见 1.1）。
- **正解**：sequence 改用官方 `document.xml` 基座（`kOfficialSequenceDocumentBody`
  + `buildOfficialSequenceDocumentPart()`，`convert.ts` 按 kind 分派）。
- **附带**：水平消息的本地 Y 符号必须与 `sign(W)` 一致（Height/几何/文字同号）。
  Visio 打开时会自行归一化到自洽状态（线落回时间格行、文字与线同 Y），
  但写入时就一致可避免重算；`Connections` 行号仍是 1-based（见 7.2）。

### 7.8 [sequence] 片段标签是**两段带**：MS6=类型关键词、MS7=参数

- **现象**（两阶段）：
  1. 标签 `[HealthCheck]` 垂直居中、与框内首条消息线重叠，且双击无法编辑；
  2. 把文字挪到子形状后，「循环」字样消失，框里只剩 `[HealthCheck]`。
- **根因**：官方片段标签是**上下两段**，文字分属两个子形状：
  - 组根 `IsTextEditTarget='0'`（不是文本编辑目标），所以标签不能写在组根上；
  - **MS6 = 关键词带**（顶边 `PinY=Sheet.5!Height`、`LocPinY=Height` 向下展开、
    `EventDblClick=OPENTEXTWIN()`），母版自带文字「循环」/「选择」；
  - **MS7 = 参数带**（紧贴关键词带下方），母版占位文字「[参数]」。
  阶段 1 把 `<Text>` 写在组根 → 按组根文本框居中；阶段 2 把 `[HealthCheck]`
  写到 MS6 → **覆盖掉关键词带**，于是「循环」被顶掉。
- **正解**：MS6 **不写文本**（继承「循环」/「选择」），mermaid 标签写 MS7；
  MS7 无标签时显式写**空文本**覆盖母版占位，否则框内多一行「[参数]」。
- **追加坑 1（白底白字）**：MS7 的文字色 = `User.DarkerColor`（`THEMEVAL("TextColor"/"FillColor"/"LineColor")`
  的 LUM 比较链），在官方 sequence 基座里解析为**色索引 28**，而基座 `Colors` 只定义
  24/25 → 未定义索引渲染成白色，配合白色填充 → 文字"消失"。实例显式写
  `Character.Color=0`（auto/黑）覆盖即可（仅在有标签时写）。
- **追加坑 2（两带压线）**：两带各 0.2445IN，合计 0.489IN ≈ 2 个时间格；片段顶边
  若落在循环体首行消息上，参数带就被消息线穿过。正解：顶边 = `rowYin(startRow) + 1.5×0.25IN`
  （上提 1.5 格），底边 = `rowYin(endRow) − 0.125IN`。
  **但**若上方紧邻一行就是已绘制消息（含自消息末行），1.5 格会把顶边抬到该消息线
  之上、横穿它（实测：opt 顶边穿过上方自消息的 C 形）。此时降到 **1 格**——顶边与
  该消息线重合，标签带底边距首条内部消息线仍有 0.011IN。判据：上方最近已绘制
  消息的末行 == `startRow − 1`。
- **证据**：`source/diag/sequence.ts` `writeFragment()`；Visio 实测
  `#20 Loop fragment PinY=1.458333 H=1（顶边 1.958333）`、
  `kid #21 mshape=6 text='循环'`、`kid #22 mshape=7 text='[HealthCheck]'`、`Char.Color=0`；
  导出 PNG 转 ASCII 复核：关键词带 CJK 字形在 156–167 行、参数带 `[HealthCheck]`
  在 186–196 行、两带分隔线 177 行、循环内首条消息线 222 行（互不重叠）。

### 7.9 [sequence] 自消息：mermaid 不产出 `self` 类型，行号必须累计

- **现象**：`A->>A: 文本` 渲染成零长直线（Width=0），箭头/文字挤在一起。
- **根因 1（类型）**：mermaid 的 db 用 `type=0`（普通箭头）表示自消息，靠 `from === to` 区分；
  提取器原样映射成 `sync`，而契约与官方母版都按独立的 `self` 语义走
  （`Self Message` 母版、`kSelfH=-0.5`）。→ 提取器补：`from === to` 且 kind 为
  sync/async/return 时改判 `self`（activate/deactivate 行同样 from===to，但 kind 不同，不受影响）。
- **根因 2（行号）**：普通消息占 1 格、自消息占 2 格（官方 Self Message 高 0.5IN = 2×0.25IN）。
  原来直接用**消息下标**当行号，自消息会和相邻消息压在同一行。→ 改为**累计行模型**
  `startRows/endRows/total`，提取器（片段/激活包围盒）与渲染器（`sequenceRows`）用同一规则。
- **证据**：mermaid 官方 SVG 实测自消息占约 2.4 行；Visio 实测
  `Self Message BeginY=3.0833 EndY=2.5833（Δ=0.5IN）`、两端钉接 `Connections.X16/X18`
  （不同行）、母版 `Self Message`、文本居中于 C 形内。
- **注意**：我们写入的 `Width=0.19685`（与官方实例逐值相同），Visio 打开后
  `ResultIU` 会报 `-0.2`（1-D 形状归一化符号）——官方实例同样如此，不影响渲染方向。

### 7.10 [sequence] 参与者列位吸附：火柴人框只有 36px 宽

- **现象**：`actor 用户` 被摆到 `x=0`（压在最左边），其余参与者正常。
- **根因（两个叠加）**：
  1. 提取器把 `x` 写成 `75 + i * X_GAP`，但 `i` 是后文 `for (var i…)` 声明的变量，
     `var` 提升后此处为 `undefined` → `x = NaN` → 契约归一化成 `0`（实测）；
  2. SVG 列位吸附的候选框阈值是 `宽≥100 / 高≥30`，而 actor（火柴人）框只有 **36×82px**
     → 永远匹配不上，于是该参与者一直用"确定性列位"（即上面那个坏值）。
- **正解**：用独立下标 `ai` 写初始列位；吸附阈值降到 `30×20`，并跳过整图框
  （`w>2000 || h>4000`）与负坐标框（`x<0 || y<0`）。
- **证据**：实测 mermaid SVG 候选框 `cx=75 w=36 h=82 :: 用户`；修复后
  `User@75 Web@275 API@556 DB@756 MQ@956`（与 mermaid 实际列位一致）。

### 7.11 [sequence/通用] Visio 会忽略 PageWidth/PageHeight 并自动缩放页面

- **现象**：写入 `PageWidth=11.96 / PageHeight=8.01`，Visio 打开后却是
  `23.80×11.69`（604.6×297mm），且**所有形状被整体平移**（X +7.77IN）。
  ER（15.34→16.04）与 class 同样中招——是**系统性**问题，只是图形小的时候
  恰好落在 A4 内、看不出异常。
- **根因**：`PageSheet/DrawingResizeType` 语义（实测三组对照）：
  `0`/`1` = 随图形自动缩放（按打印纸倍数放大页面，**PageWidth/PageHeight 被忽略**）；
  **`2` = 不缩放**（页面尺寸 = 写入值，形状坐标不动）。官方样本也是 `1`，
  但官方样本图形小、正好落在 A4 内，所以没暴露。
- **正解**：`buildPagesXml` 增加 `drawingResizeType` 选项，sequence 分支先传 `'2'`；
  2026-09 起全图型默认 `'2'`，页面严格等于内容外包围框加两倍半线宽。
  实测三个序列产物打开后页面尺寸与写入值**逐位一致**（7.79×3.01 / 7.79×3.76 / 11.96×8.01），
  形状包围盒也都在页面内。
- **后续**：class/er 切到 `2` 前要先修布局，否则会从"页面偏大"变成"内容出页"；
  这一步已随画布统一修复落地，只剩审计器收尾，见
  `docs/待讨论功能备忘.md` P-4。

### 7.12 [sequence] alt 是「容器 + 操作数」，不是两段带

- **现象**：mermaid `alt/else` 此前被跳过（无母版素材）；即使补上母版，按 loop/opt 的
  "两段带"写法也会错——`Alternative fragment` 母版**只有 MS6（折角标题带）**，没有 MS7。
- **根因/官方代数**（`seq-all-in-one` 实测）：
  - `Alternative fragment`（MasterType=2）= **列表容器**：`msvStructureType='List'`、
    `msvSDListItemMaster=USE({08EAEFF2-…})`（= Interaction operand）；根 Geometry IX=0 画整框；
    唯一子形状 MS6 是**折角标题带**（`msvStructureType='Heading'`，Geometry 用 `TxtWidth` 折角，
    文字「替换」）；`Control.Row_1.X = BOUND(75MM,0,FALSE,1MM,500MM)` 是列表宽度控制。
  - `Interaction operand`（MasterType=2）= **顶层独立形状**（不是容器的子形状！）：
    `LinePattern=2`（虚线）、Geometry IX=0 的 `NoShow = IF(LISTORDER()=1,TRUE,FALSE)`
    （首条分支不画分隔线）、文本占位「[条件]」、母版默认高 0.9842IN。
  - 官方实例：容器 PinY=16.0396/H=2.2130，两个操作数 PinY=15.4252/16.4094（间距 0.9842）、
    `Relationships=SUM(DEPENDSON(…))` 挂到容器——即"分支高度 = 操作数高度"的列表布局。
- **正解**（`writeAlternativeFragment` + `writeOperands`）：容器写 PinX/PinY/Width/Height +
  Control.Row_1 + Geometry IX=0 + 仅 MS6（`PinY=Height` 贴顶）；每个分支写一个顶层
  Interaction operand：`PinX=容器X`、`Width=容器宽`、**高度按分支实际跨度覆写**、
  首条 `NoShow=1`、文本 = 分支条件（mermaid 的 `alt`/`else` 标签）。
- **坑（实例 cell 的 `F='Inh'`）**：操作数的 `PinX/PinY/Width/Height` **不能写 `F='Inh'`**——
  母版 Width 公式是 `IFERROR(LISTSHEETREF()!Controls.ROW_1,User.UserWidth)`，我们的形状
  不在 Visio 列表里 → `LISTSHEETREF()` 失败 → 回退母版默认值（实测四个操作数全被摆回
  `PinX=PinY=1.9685`、`W=1.8898`）。只有 `LocPin*` 写 `Inh` 是安全的（母版公式引用自身 Width）。
- **证据**：Visio 实测 15-sequence-4：`Alternative fragment W=5 H=1.875`、
  `Interaction operand #37 H=0.6305 / #38 H=1`（首条 NoShow=1）；PNG→ASCII 可见
  「替换」标题带 + 两条分支条件 + 分支间虚线。

### 7.13 [sequence] 备注（note）：seq-all-in-one 没有 Note 母版，复用 class 包的官方 Note

- **事实**：`seq-all-in-one` 只有 12 枚时序专用件，**不含 Note**；`Note` 母版在
  `class` 包（`kClassTemplates['Note']`）。母版目录跨记录可见（`buildMasterCatalog` 把
  class 记录排在 seq 记录之前，`MasterPacker` 会依次查找），所以 sequence 分支直接
  `push('Note')` 即可取到官方 Note 母版。
- **坑 1（子形状）**：Note 是 Group + 折角子形状 MS6。实例不写 MS6 时 Visio 按母版子 ID
  现场实例化，多个 Note 的子形状 ID 冲突 → **3 个 Note 只剩 1 个**（与生命线同一坑）。
  正解：显式写 `<Shape ID=… MasterShape="6" Type="Shape"/>`，单元格全继承（母版公式
  引用父级 `Sheet.5!Width/Height`，不用手写）。
- **坑 2（宽度/折行）**：Note 母版 `Height = GUARD(MAX(CEILING(TxtHeight,1.5MM),8MM))`，
  `TxtHeight = TEXTHEIGHT(TheText,TxtWidth)`；实例必须写 `TxtWidth = Width`，否则母版默认
  按 0.98IN 折行。且**文档默认字号是 12pt（0.1667IN）**——按 9pt 估宽会偏窄：
  实测「失败时需当日对账」（8 汉字）在 1.42IN 宽下折成 2 行（H=0.5315 撑出 2 格槽位），
  按 `0.17IN/汉字 + 0.095IN/其他 + 0.3IN` 估到 1.66IN 后恢复单行（H=0.3543）。
- **行模型**：note 占 **2 格**（0.5IN 槽位），与自消息同一累计规则；片段顶边避让必须
  把 note 算作"上方已绘制内容"（否则片段顶边会横穿备注）。
- **证据**：`source/diag/sequence.ts` `writeNote()`/`noteWidth()`；Visio 实测
  `Note PinX=5.9896 W=1.66 H=0.3543 TxtWidth=1.66 Char.Size=0.1667`。
- **证据**：`temp/page-probe.ps1`（PageSheet + 形状包围盒）、`temp/patch-page.mjs`
  （改单元格重打包对照）；提交见 README 索引。

## 8. 下游嵌入（docx / OLE）

### 8.0 [通用] 缺「页→母版」关系件，母版不在页面的关系闭包里

- **现象**：产物单独打开正常，嵌进 docx 后就地激活时首帧按"母版未解析"作画；
  把同一份产物在 Visio 里打开重存一次，问题消失。
- **根因**：`/visio/pages/_rels/page1.xml.rels`（页部件 → 本页用到的每个母版一条
  `Type=".../relationships/master"`）我们从来没生成过。官方 15 份样本里除自产的
  `c4-1` 外 14 份都有这一件；缺了它，按 OPC 关系从页面出发根本走不到母版件，
  惰性加载路径自然拿不到母版几何。
- **正解**：`PartsAssembler.addPageMasterRels()` 扫描页内形状的 `Master="N"`，
  经 `masters.xml` 的 `<Rel r:id>` 与 `masters/_rels/masters.xml.rels` 解析出文件名，
  按首次出现序生成 `Target="../masters/masterN.xml"`；一次覆盖全部图型。
  `tests/spec.test.ts` 的 `mustParts` 增加断言：页内用了母版就必须有此件，
  且每个 Target 必须存在。
- **证据**：对照用户提供的 Visio 重存件，逐件 diff 得到该差异（2026-09-24）；
  补件后四个图型的母版条数与重存件一致（block 1、class 8、er 5、flowchart 3），
  Target 全部存在，`npm test` 49 项全绿。

### 8.1 [通用] 节点实例是空壳 → OLE 激活首帧按母版默认尺寸作画

- **现象**：同一份 vsdx，单独打开正常；从 docx 里双击对象就地激活时，每个节点的
  **选中框位置与大小都对，画出来的背景框尺寸却差一个量级**，缩放或滚动一次后恢复。
  Word 里不显示图是另一回事（呈现缓存），与本条无关。
- **根因**：OLE 激活路径的首帧没有解析母版继承，直接按母版几何作画；母版占位
  40×30mm，远大于 mermaid 布局间距（`source/diag/common.ts` 的实例尺寸覆盖注释
  记录了同一事实）。选中框读的是实例 Cell，所以是对的。
- **正解（basic 家族已实施，分支 `feat/p7-node-materialize`）**：节点 shape 自己写出
  `Section N='Connection'`（四边中点加中心共 5 行，只写 `X/Y`）与
  `Section N='Geometry' IX='0'`（`MoveTo` 加三段 `LineTo` 再一条闭合行，本地坐标，
  每格 `V` 值加 `F='Inh'`），另补 `ObjType='1'`；`Master` 保留作样式来源；
  连线已写实，不动。连线与节点都只照抄 Visio 保存态，不自己发明公式。
  自检四条：节点有 Geometry、顶点落在自己框内、节点有 Connection、
  连线有 Geometry（最后一条不判越界）。class/er/sequence 的成员行与容器不在这一批。
- **证据**：写实后的产物嵌入 docx、就地激活不再错乱（2026-09-24 实测）；结构对照与
  完整排查在 tool-documentor 的 `docs/WORD处理经验/05-VSDX形状写实与首帧渲染.md`。
  官方样本本来就是写实态：`basic-5` 3 段 `Geometry` 加 2 段 `Connection`、
  `class-all-in-one` 56 加 19，空壳才是偏离样本。
  本仓实测：`tests/spec.test.ts` 加写实判据后 49 项全绿；block 与两份 flowchart 的
  XForm 逐值未变（6/6、7/7、31/31），Visio 读回页面尺寸与形状几何与写实前一致；
  class / er / sequence 产物与本批逐字节相同，未受影响。

### 8.2 [通用] 连线走 **全自动**，不自算端点选边、不自算走线（已决）

- **决策**：连线保持"全自动"形态——
  `BeginX/EndX` 走 `_WALKGLUE(BegTrigger,EndTrigger,WalkPreference)`、
  `WalkPreference=3`、`ConFixedCode=6`、`Connects→ToCell='PinY' ToPart='3'`、
  端点按容差（0.15in）吸到最近连接点、实例几何烘一条 L 型缓存。
  **不做**自算端点选边、**不做**自算走线、**不做**全局障碍物规避。
- **为什么定这条**：试过一轮"自算端点 + 自算折线"（分支 `fix/connector-endpoint-pinning`，
  6 个提交，未合并）。收益只在"不重算那条路"（Word/OLE 首帧、下游预览）上可见；
  Visio 打开本来就会按 WALKGLUE 重算走线，我们烘什么它都覆盖。代价则是：
  走线一变，渲染基线、金标准、逐字节闸门全要重建；而复杂图上的"线穿节点"
  本质是**没有障碍物规避能力**——那是 Visio 这类专业软件的看家本事（动态连接线 + 路由器），
  自研等于另一个产品级工程，收益与风险不匹配。
- **两条仍然值得留的经验**（下一轮排查直接可用）：
  ① **判据要写"端点是否落在连接点上"**，不能写"是否落在轮廓上"——端点落在轮廓上但离连接点
  15~27pt 时，Visio 会按连接点重画（实测某条差 27.4pt），而旧判据 0.00pt 全绿、看不见；
  ② **先量变量再动手**：K1 控制变量实验（我们的包 + 我们的页面，只把 12 条连线的
  端点/派生值/几何/Connects 换成 Visio 重存值 → 首帧正确）证明"钉不钉不是变量"，
  直接否掉了我第一版"改成静态钉接"的方案。改动前先做这种单变量对照，比连改三轮便宜。
- **边界**：如果将来"mermaid 原图不穿、我们穿"的条数持续偏多，先用
  `temp/crossing-audit.mjs`（按烘进几何的折线测是否穿过非端点形状框）定位到具体连线——
  那属于"我们丢拐点"的 bug；"mermaid 自己也穿"的部分照抄不修。
  内容侧还有更便宜的一张牌：调 `direction`、拆并 `subgraph`、把跨层边改走相邻层。
- **证据**：`git log master..fix/connector-endpoint-pinning`（试验全过程与每次实测数据）；
  恢复后的形态画像：`WALKGLUE 12 / ConFixedCode 3 / WalkPreference 15 / PAR(PNT 0 /
  ToCell=PinY 6`；`npm test` 53 项全绿；9 份样本渲染与 Visio 重存态逐字节一致。

### 8.3 [通用] 画布按比例外扩：页面 = 内容 × 1.1

- **背景**：画布原本是"内容盒 + 半线宽"（`kCanvasMargin = 0.0053IN`）——**零余量、刚好贴合**。
  而连线走全自动（`_WALKGLUE` + 不写 `ConFixedCode`），Visio 打开时会**自己重算走线**，
  它的绕行可以伸到内容盒之外：我们只能保证自己烘的缓存在页内，Visio 重算后的走线事先不可知。
  没有余量时这种外凸会被页边裁掉（"画布不够"）。
- **正解（分支 `fix/canvas-slack-ratio`，`kCanvasSlackRatio = 0.05`）**：页面 = 内容 + 2×(半线宽 +
  内容尺寸 × 比例) = 内容 × 1.1。**用比例而不是固定英寸**：固定值会改长宽比
  （06 号 2.51×14.93IN 加 0.2IN 后比例从 1:5.95 变 1:5.58，偏 6%），按比例则两轴同倍率、
  页面比例 == 内容比例。按轴给边距（x 用内容宽、y 用内容高）。
- **口径必须一致**：页面装配（`pageInchSize`）与形状/连线坐标平移（`writeShapeNode` /
  `writeConnectorNode` / `snapToConnectionPoint`）**共用同一组边距**，class/er 的 `boxExtent`
  与 sequence 的坐标映射同理——两边不一致就会"内容偏出页面"（这正是第一版固定余量时
  险些踩的坑：`buildPagesXml` 加一次、平移再加一次）。
- **实测**（`temp/page-ratio.mjs` + `temp/visio-overflow.ps1`，后者用 Visio 解析母版继承）：
  9 份样本页面/内容两轴均 ≈ 1.10、比例不失真；四边外凸 0；9 份渲染与 Visio 重存态逐字节一致；
  53 项测试全绿。小图（0.7IN 级）因内容盒取整，倍率会有 ~1% 偏差，可接受。
- **注意**：外扩改变页面尺寸 ⇒ 对象框比例随之微调；这是预期变化，不是回归。
