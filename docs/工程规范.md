## 1. 提交规范

### 1.1 格式

```
<type>: <中文摘要>

1. <要点一>
2. <要点二>
3. <要点三>
```

- 标题：`type: ` + 中文摘要，一行、动词开头、简洁（≤ 50 字）
- 正文：空一行后接**有序列表** 3～5 条，总结关键要点、不赘述；
  没有值得列出的要点时可省略正文
- type 枚举：`feat` 新功能 / `fix` 缺陷修复 / `refactor` 重构（不改行为）/
  `docs` 文档 / `test` 测试 / `chore` 构建·依赖·杂项
- **提交消息用 `-m` 数组分段**（每段一条要点），不要 heredoc——Windows
  控制台 GBK 会把 UTF-8 中文写坏

### 1.2 工作流习惯

- 一个逻辑变更一个提交：`fix:` 与 `feat:` 分开，即使同批完成
- 提交前 `git status --porcelain` 确认只含目标文件；`git add` 指定文件
- 工作树必须干净才算一轮完成
- 用户要求修改 → 追加新提交，不 rewrite 历史

### 1.3 版本管理（摘要，完整见 dsh-plugins 根《版本管理规范》）

- SemVer 子集 `0.1.0` / `0.1.0-rc.N`
- **集成发布不升版本号**（commit hash / git tag 标识批次）；
  定版发布由用户专门发起、是唯一升号场合
- 候选期缺陷修复同版本重发，不把 rc.N 当补丁计数器

## 2. 代码与命名规范（TS 工程裁剪版）

### 2.1 文件与目录

| 类别 | 规则 | 示例 |
|---|---|---|
| 模块（core/xml/opcpkg/...） | 目录小写语义名 | `src/core/`、`src/opcpkg/` |
| 模块内文件 | 小写语义名（单文件一职责） | `partUri.ts`、`xmlNode.ts` |
| 契约/类型集中文件 | 小写语义名 | `types.ts`、`contract.ts` |
| 测试 | `<套件名>.test.ts`（vitest 默认发现；保留 C++ 套件名便于对照） | `testir.test.ts`、`testopc.test.ts` |
| 脚本 | `*.mjs`（ESM） | `make-fixtures.mjs` |

### 2.2 TypeScript 标识符

- 接口/类型：PascalCase，`CreateOptions`、`SnapshotResult`（类型名即文档）
- 函数：camelCase 动词开头，`jsonToDiagram`、`defaultNode`
- 常量：UPPER_SNAKE（模块顶部命名常量，如 `kDefaultPort` 对照 C++ k 前缀亦可）；
  外部可调参数走 options / 参数，不散落魔数
- 布尔状态：语义化形态（`ok`、`milestone`、`merge`）
- **禁止**：`any`；未使用的 import/变量（typecheck 全绿为提交门槛）
  ——tsconfig 开启 `strict` + `noUncheckedIndexedAccess` + `noUnusedLocals` +
  `noUnusedParameters`，数组/Map 取值显式判空

### 2.3 注释与文案

- 文件头注释说明职责与"为什么"；关键机制（数字格式化规则、U/V/F/E 语义、
  顺序即协议处）必须留注释
- **注释用中文，代码标识符用英文**（取舍说明：terminal 版如此；fileexplorer/
  textviewer 版为英文注释——本仓库是 C++ 中文注释工程的中文文档平移，
  选中文注释以保对照性；如需英文注释请指正）
- 对外错误消息用中文（服务/CLI 用户可见面），代码内消息字符串跟随 C++
  原样（英文短语 + [phase] 前缀）——以可读与对照优先

### 2.4 工程纪律（移植特有，见 port-plan 00 §3/§5）

- 类型即契约：跨模块流转全部走 core 类型，禁止隐式 any 通道
- 顺序即协议：产物顺序（XML 子元素/部件/ZIP 条目）照抄 C++，不"优化"
- 常量照抄不优化：布局常量、魔数缓存、哈希规则改动即产物漂移
- 软失败与硬失败分界：求值失败/缺资源 → 软（no-op/保留原件）；
  输入校验/契约错误 → 硬（抛错中止）
- typecheck + 测试全绿为每轮（提交）门槛
