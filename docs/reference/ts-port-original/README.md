## 2. 总体结论（TL;DR）

### 2.1 工程一句话

**mmd2vsdx v2** 是一个 C++17 的 Mermaid→VSDX 转换器：Node.js + Chromium
（mermaid-snapshot）负责渲染与结构提取，C++ 引擎负责把 IR 翻译成原生可编辑
的 Visio VSDX（OPC/ZIP/XML + 官方模具母版实例）。规模约 **4.1 万行 C++**
（其中 2.8 万行是生成的模具嵌入资源）+ **1.6 千行 JS** 提取层 + 16 个验收样本。

### 2.2 效率结论（详见 01）

| 维度 | 结论 |
|---|---|
| 运行性能 | **不降反升**：瓶颈在 Chromium 渲染（每次 0.5–2s），与语言无关；TS 化后去掉子进程 + HTTP 桥接（每图省 ~5–20ms 编排开销），纯计算路径（JSON→XML→ZIP）Node 原生能力与 C++ 相当 |
| 内存 | 基线略高（Node ~50MB vs C++ ~10MB），对本负载（单图 ≤ 几 MB）无影响 |
| CLI 单次启动 | Node 冷启动 + 浏览器拉起 (~1–2s) 比 C++ 冷启动 (~10ms) 慢；**对策：常驻服务形态 / 预热 / 按需启动**，批量与服务场景无感知 |
| 开发效率 | **显著提升**：单语言单工具链、提取层与转换层共享类型、免 libxml2/zlib/WinHTTP/CMake 四套外部依赖、免 FFI、天然跨平台、npm 分发、可进浏览器/Worker |
| 维护成本 | 测试框架（doctest→vitest）、构建（CMake→tsc/tsup）全简化；stencil 资源改为生成式 TS 资产，规则可审计 |

**结论：效率不会下降。** 在"以服务/批量为主要使用形态"的前提下，运行时
效率持平或更好；在开发、维护、交付、生态集成效率上全面占优。唯一明显代价是
单次 CLI 冷启动，用常驻服务形态化解。

### 2.3 移植策略一句话

**逐模块 1:1 平移 + 同构保留**：保持 v2 七模块架构与门面对门面契约不变，
C++ 模块按 `core → xml/opcpkg → vsdxdoc → mmdtransform → app` 顺序平移为
TS 包（monorepo），mermaid-snapshot 提取层原样并入 TS 生态（补类型），
stencil 资源继续用脚本从官方模具生成 TS 资产，测试以 8 套 C++ 测试为蓝本
平移为 vitest 套件，16 个 .mmd 样本 + 产物往返校验作为验收金标准。
