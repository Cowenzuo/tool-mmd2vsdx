> 承接 02 需求规格。本文给出 TS 端实现的整体方案：模块映射、依赖图、
> 目录结构、构建与发布、分阶段实施计划。04–06 展开各层实现细节。

## 1. 核心策略：逐模块 1:1 平移 + 同构保留

```
C++ v2 七模块                  TS 实现
─────────────────────────────────────────────────────────────
core（数据层）        →  src/core/          （类型 + 常量 + 错误）
xml（libxml2 封装）   →  src/xml/           （轻量 XML 树 + 序列化 + XmlBuilder）
opcpkg（OPC 容器）    →  src/opcpkg/        （PartUri/CT/Rels/Zip/Package）
http（通信层）        →  src/http/          （可选兼容层：server + snapshot HTTP 模式）
mmdtransform         →  src/mmdtransform/   （Translator + jsonToDiagram + 渲染器门面）
vsdxdoc              →  src/vsdxdoc/        （translate/docmodel/render/serialize/masters）
app                  →  src/app/           （Application + CLI + serve）
mermaid-snapshot     →  src/snapshot/       （收编：mermaid 渲染 + extract TS）
```

原则：
1. **门面对门面契约不变**：`Translator → Diagram → VsdxTranslator → XmlParts → OpcPackager`
   的数据流原样保留，模块边界不变，便于对照 C++ 版逐文件核查。
2. **进程内直调优先**：mmdtransform 不再经 HTTP 调 snapshot，直接调用
   `src/snapshot` 的 `renderDiagram(text)`；HTTP 服务形态降级为可选兼容层
   （TS-205 P2）。
3. **类型即契约**：core 的 IR/契约类型与 snapshot 的返回类型共用同一
   `SnapshotResult` 接口，跨模块流转全部类型化。
4. **生成资源不改逻辑**：stencilresources 由脚本生成 TS 资产（见 05 §4.1）。

## 2. TS 架构与依赖图

```
src/
├── core/            ← 零依赖（纯类型 + 常量 + 错误类）
├── xml/             ← 依赖 core
├── opcpkg/          ← 依赖 core、xml
├── snapshot/        ← 依赖 mermaid/playwright（npm），产出 SnapshotResult（core 类型）
├── mmdtransform/    ← 依赖 core、snapshot（进程内）或 http（回退）
├── vsdxdoc/         ← 依赖 core、xml、opcpkg
├── http/            ← 依赖 core（可选；serve 形态用 node:http）
├── app/             ← 依赖全部（编排）
└── cli.ts           ← app 的 CLI 入口
```

```
app ──┬─→ mmdtransform ──→ snapshot ──（mermaid + playwright）
      │        └─────────→ http（可选回退）
      ├─→ vsdxdoc ──→ xml ──→ core
      │        └──→ opcpkg ──→ xml
      └─→ http（serve）
```

与 C++ 版差异：`snapshot`（原 mermaid-snapshot 目录）从"外部子进程"变为
**仓库内第一等模块**；`http` 从"必需"降为"可选"。

## 4. 关键工程决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 包结构 | 单包（非 monorepo） | 规模 ~1 万行，单包简单；如未来拆分 snapshot 独立再升级 workspaces |
| 模块系统 | ESM（"type":"module"） | 与现有 .mjs 一致；Playwright/mermaid 均为 ESM 友好 |
| XML | 自研轻量树（~300 行），不引 fast-xml-parser | XmlBuilder 是"构建"为主，解析仅 roundtrip/资源用；自研可精确控制转义与命名空间；少一个依赖 |
| ZIP | node:zlib（deflateRawSync/inflateRawSync）+ 自研容器封装 | 原生 C++ 速度；自研 300–400 行（CRC32 表 + 头/中央目录） |
| 数字格式化 | 自研 `formatNumber`（对标 C++ 输出规则） | 见 04 §3.2，语义等价验收下允许差异 |
| Playwright | 进程内单例 + 串行队列 + 预热 | 与现状等价；失败自动重建页面 |
| 校验 | 手写守卫（不引 zod） | 字段少、边界明确；zod 留 P2 可选 |
| 测试 | vitest（node 环境为主 + 少量 chromium 环境） | 同一生态；e2e 用真实 Playwright |
| 构建 | tsc 编译 + esbuild/tsup 打包 CLI | CLI 单文件可执行（node 22 支持直接执行 .ts，也可打包） |

## 5. 构建 / 测试 / 发布

```bash
npm install                        # mermaid + playwright（+ dev: vitest/typescript）
npx playwright install chromium    # 浏览器（可选步骤，CI 与开发机）
npm run gen:stencils               # 生成 src/vsdxdoc/masters/stencilData.ts（P1）
npm run build:extract              # 生成 snapshot bundle（P1；P0 可先直接用源码）
npm run build                      # tsc -p .
npm test                           # vitest run（8 套）
npm run e2e                        # teste2e（真实渲染，需 chromium）
```

发布：
- `bin`: `mmd2vsdx` → `dist/cli.js`
- 包内容：`dist/` + `stencilData.ts`（生成，随包？见 02 TS-908：**默认不随包**，
  由 `mmd2vsdx prepare-stencils --visio-dir ...` 生成到用户目录或本地 node_modules 覆写；
  提供"无模具模式"（本地几何，对应 CreateOptions.useConnectorMaster=false 语义））
- engines: node >= 22

## 6. 分阶段实施计划（里程碑）

| 阶段 | 内容 | 交付验证 | 对应需求 |
|---|---|---|---|
| **M0 骨架** | 包脚手架 + tsconfig/vitest + core 全类型 + errors | testir 绿 | TS-100~106 |
| **M1 容器层** | xml（树/序列化/XmlBuilder/常量）+ opcpkg（PartUri/CT/Rels/Zip/Package/OpcPackager） | testopc 绿；能用 C++ 产物 roundtrip 打开 | TS-400~506 |
| **M2 翻译主干** | jsonToDiagram + docmodel + coordinateTransform + DiagramImporter（通用分支）+ serialize + 最小 renderer（Rect 等五种几何）+ connectorBinder | testjson/testtranslate 绿；**fixture JSON → 可打开 .vsdx** | TS-301/601~605/607 |
| **M3 snapshot 收编** | renderer.ts（Playwright 生命周期 + 进程内 renderDiagram）+ extract 收编 + 图型类型化 | testparser 绿；**真实文本 → .vsdx**（16 样本通用图型全过） | TS-200~206/302 |
| **M4 专用渲染器** | gantt/git/pie/quadrant/sequence 五渲染器 + 多页 | 样本 07/08/12/13/15 产物结构校验通过 | TS-606/610 |
| **M5 masters** | MasterLibrary 平移 + gen-stencils + applyInstanceOverrides + mergeStyles | testmasters 绿；产物含母版实例（Visio 打开验证） | TS-608/609 |
| **M6 编排与发布** | app/CLI/serve/ConvertResult + roundtrip + e2e + 性能对比（≤1.2×）+ npm 发布准备 | 8 套全绿；16 样本金标准通过 | TS-700~804/901~908 |

> 每阶段红线：构建 + 对应测试全绿（与 C++ 版"每阶段重构完成"纪律一致）。
> M0–M2 可完全离线（无浏览器依赖），M3 起需要 chromium。

## 7. 风险预案（实施期）

| 风险 | 预案 |
|---|---|
| libxml2 序列化细节与自研序列化器行为差异 | M1 用 C++ 产物部件做"解析→重序列化→数值等价"对照测试 |
| zip 写入被 Visio 拒绝 | 以 C++ 产物 zip 结构为基准逐字段对照（04 §4）；用 7-Zip/Windows 解压 + roundtrip 双重验证 |
| 专用渲染器数值规则（gantt 1,490 行） | 平移时保留 C++ 的**分步注释与常量命名**，逐函数对照，先跑样本 07 结构校验再优化 |
| extract bundle 拼接机制在 TS 下的兼容 | M3 先保留 .mjs 原样（P1 再 TS 化），用 build-extract 生成 IIFE，行为零风险 |
| Playwright 版本升级行为漂移 | package.json 锁 playwright 主版本；e2e 金标准兜底 |
